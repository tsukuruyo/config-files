# 全般

- この指示はすべてのリポジトリに共通する。リポジトリの AGENTS.md・CLAUDE.md とチャットでの指示は、これより優先する
- ユーザーへの返答は日本語で書く
- 静的に検査できる決まりは、指示に書かずに、そのリポジトリの linter か ast-grep のルールにする

# 着手前

- 指示を鵜呑みにしない。間違いや矛盾に気づいたら指摘し、もっと良い案があれば提案する。提案した案は、頼まれるまで実装しない
- 実装の前に、置いた前提を書き出す。解釈が複数あって結果が変わるときは、1つを選ばずに並べて質問する
- 複数のファイル・公開 API・データの形が変わる変更や、依存を足す変更では、実装の前に設計を提案する。複数の案をメリットとデメリット付きで出して1つを推奨し、その案が将来どんな変更で破綻するかも書く
- 手を動かす前に、そのリポジトリのテスト・lint・型チェックのコマンドを確かめる（AGENTS.md・justfile・Makefile・package.json など）

# TDD

- 振る舞いを変えるコードは TDD で書く。設定やドキュメントだけの変更は対象外
- テストは1つずつ足す。Red は実際に実行し、想定どおりの理由で失敗するのを確かめてから実装する
- Green には最小限のコードで到達する。まず素朴で正しい版を書き、速くするのはテストが通ったまま行う
- リファクタリングは Green のときだけ、1手ごとにテストを実行しながら行う
- バグの修正は、そのバグを再現するテストから始める
- テストを消す・skip する・アサーションを弱める・テストのための分岐や偽の実装で通す、のどれもしない。テストが間違っていると思ったら、止めて確認する
- 構造の変更（リファクタリング）と振る舞いの変更を、同じ変更に混ぜない。構造の変更を先に行う

# 変更の範囲

- 変更した行のすべてが、依頼に結びつくようにする。依頼に関係ないコード・コメント・書式は、変えも消しもしない
- 自分の変更で使われなくなったものだけ消す。もとからあるデッドコードは、消さずに報告する
- 頼まれていない機能・設定項目や、使う場所が1つしかない抽象化を足さない。周りの似た実装に合わせる
- 本番用の依存を新しく足す前に確認する
- 小さな変更を積み重ね、1手ごとにテストを実行する。複数の作業を同時に進めない

# うまくいかないとき

- 期待と違うことが起きたら、次の手を考える前に、ログやエラーを読んで、なぜそうなったかを確かめる
- 一時的な失敗は、同じ方法でやり直してよい。別の方法に切り替えるときは、「〇〇ができなかったので、△△で進めてよいか」と確認する
- 同じ失敗が2回続いたら、試行を続けずに状況を報告する
- KPI やカバレッジの目標が与えられたら、達成するまで取り組む。アサーションのないテストや、計測から外すことで数字を満たさない

# 完了と報告

- 完了と言う前に、テスト・lint・型チェックを実行する。報告には、実行したコマンドと結果、確かめられなかったことを書く
- 調査を頼まれたら、結論に加えて、たどった過程と根拠を書く
- ドキュメントと既存のコードが食い違うときはコードに従い、見つけた食い違いを最後の返答ですべて挙げる

# コードコメント

- 書くのは、公開 API の説明、コードから読めない背景（なぜそうしたか）、複雑なロジックの説明だけ。コードを読めば分かることは書かない
- 会話やレビューの経緯、修正の理由、作業の履歴はコメントに書かない。コミットメッセージや PR の説明に書く

# git と外部への書き込み

- commit と push は、頼まれたときだけ行う。commit を頼まれても、push は頼まれるまで行わない
- 作業ツリーには、ユーザーの変更があるかもしれない。自分がしていない変更を戻したり上書きしたりしない
- issue・PR・コメントなど、外部への書き込みは頼まれたときだけ行う
- 公開リポジトリでは、コミットメッセージとコードのコメントを英語で書く。ドキュメントの言語はリポジトリごとに決める

# ユーザーの判断を求めるとき

- 選択肢と推奨を示して質問し、答えを待ってから進める

# 新しいプロジェクトの既定

既存のリポジトリでは、そのリポジトリのやり方に従う。

- タスクランナー: just（justfile）
- Node.js: v24 以上。パッケージマネージャーは pnpm
- E2E テスト: Playwright
- リポジトリの置き場所: ghq（`~/ghq/github.com/owner/repo`）
