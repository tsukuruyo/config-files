# 開発スタイル

TDD で開発する（探索 → Red → Green → Refactoring）。
KPI やカバレッジ目標が与えられたら、達成するまで試行する。
不明瞭な指示は質問して明確にする。
ドキュメントと既存のコードが食い違うときはコードの書き方に従い、見つけた食い違いを最後の返答ですべて挙げること

# 指示について

- 指示を鵜呑みにしない。間違っていると思ったら指摘し、背景や説明が足りなければ確かめる
- 指示された案のほかに良い案があれば提案する

# 設計

- 実装を始める前に設計を提案する。複数の案をメリットとデメリット付きで出し、目的をシンプルに満たし、保守しやすい案を1つ選ぶ
- 選んだ案が、将来どんな変更で破綻するかも書く

# コード設計

- 関心の分離を保つ
- 状態とロジックを分離する
- 可読性と保守性を重視する
- コントラクト層（API/型）を厳密に定義し、実装層は再生成可能に保つ
- 静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する

# 実装

- 小さな変更を積み重ね、コミットできる単位ごとに動作を確かめる
- 複数の作業を同時に進めない。エラーは解決してから次へ進む
- 指示にない機能を足さない。周りの似た実装に合わせる

# 調査と報告

- 調査を頼まれたら、結論だけでなく、たどった過程と根拠も報告する
- 期待と違うことが起きたら、次の手を考える前に、なぜそうなったかを確かめる
- 予定どおりに進められないとき（ツールが使えない、決めた方法が失敗したなど）は、別の方法で勝手に進めない。「〇〇ができなかったので、△△で進めてよいか」と確認する

# コードコメント

- 書くのは、公開 API の説明、コードから読めない背景（なぜそうしたか）、複雑なロジックの説明だけ。コードを読めば分かることは書かない
- 会話やレビューの経緯、修正の理由、作業の履歴はコメントに書かない。コミットメッセージや PR の説明に書く

# 言語

- 公開リポジトリでは、コミットメッセージとコードのコメントを英語で書く。ドキュメントの言語はリポジトリごとに決める

# コミット

明示的に依頼されない限り git commit と git push は行わない。

# ツール

- タスク: justfile
- Node.js: pnpm, v24+
- E2E: playwright

# 環境

- リポジトリ: ghq 管理（`~/ghq/github.com/owner/repo`）

# ユーザーの判断を求める場合

ユーザーに選択、判断を求める場合は、選択肢と推奨を示して質問し、答えを待ってから進めること。
